# Performance decision record — 2026-09-12

Keep the current JSON parser, sorted-level structure, and single ingestion event loop.
The current measurements do not demonstrate a benefit from replacing any of them.
This is a decision about the measured workload, not a claim of unlimited capacity.

## Workload and evidence

The repaired harness uses the production parsers, manager, detector, SQLite writer,
and broadcaster with a real production-built dashboard. It models 27 books with 500
levels per side, 80% deeper-book changes and 20% best-size changes, including inserts
and deletes. Binance.US remains USDT; the two USD venues share nine markets, giving
18 dashboard rows. One USD market stays profitable to exercise writes and delivery.

Two 10-second runs at each of 110 and 1,100 events/second used the documented 5-second
burst cycle, warmup, and bounded drain. These short modeled runs are exploratory
baselines, not captured internet traffic, a dedicated idle-host comparison, or a
24-hour soak. Environment: Windows 11 build 26200, Python 3.12.10, Chrome
152.0.7977.83, 16 logical CPUs, 15.65 GiB RAM. Each report includes the command and
matching before/after source fingerprints. The diagnostic code is committed in
`6d339c6`; the capacity run preceded its diagnostic-timer correction and has its own
fingerprint. No measured production behavior was changed between those two modes.

| Average events/s | Mean process CPU, one core | Receive→detect p99 | Send→detect p99 | Event-loop lag p99 | Peak RSS |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 110 | 3.40–3.83% | 0.762–0.765 ms | 22.5–44.1 ms | 23.7–24.9 ms | 74.3–75.0 MiB |
| 1,100 | 27.15–27.62% | 0.684–0.900 ms | 447.7–653.7 ms | 19.5–20.3 ms | 79.6 MiB |

All four runs processed every sent event with zero gaps/reconnects, persistence drops,
dashboard queue overflows, or browser page errors. Generator lag was also nonzero
(15–33 ms p99), so the host scheduler contributes to these latency observations.

## Diagnostic attribution and its limits

The separate 1,100/s profile partitions **exclusive elapsed function time**. It does
not measure exact CPU per stage, and its overhead makes its latency unsuitable as a
capacity baseline. Cumulative times overlap and are deliberately not summed.

| Stage | Exclusive time |
| --- | ---: |
| JSON decoding/encoding | 0.2785 s |
| Adapter Decimal conversion | 0.0712 s |
| Sorted-level insertion/update/removal | 0.1190 s |
| Detector | 0.0776 s |
| Persistence on the main thread | 0.0189 s |
| Broadcaster and WebSocket delivery | 0.2542 s |
| Event-loop wait | 6.6145 s |
| Other functions, scheduling and instrumentation | 5.3106 s |

The large remainder includes normalization, eligibility, metrics, async scheduling,
socket handling and instrumentation. It is not evidence that any single named stage
causes the observed backlog. SQLite worker-thread CPU is excluded from cProfile but
included in process CPU sampling. The current dashboard has no mounted React profiling
wrappers, which the report records as unavailable rather than a zero render cost.

An attempted Windows thread-CPU timer produced negative self times and was rejected.
Its raw diagnostic remains ignored locally; it is not included as supporting evidence.
The standard high-resolution elapsed timer produced nonnegative, additive self times.

Source: [accepted diagnostic](arb022-profile-20260912T084115Z.json).

The SQLite worker gap was measured separately with the operating system's per-thread
CPU clock around every function executed by `aiosqlite`. Three 60-second diagnostic
runs at 1,100 events/second produced the following results:

| Run | SQLite worker CPU | Main-thread persistence self time | Process CPU, one core | Send-to-detect p99 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.203 s | 0.116 s | 55.49% | 1,692 ms |
| 2 | 0.094 s | 0.085 s | 41.97% | 2,229 ms |
| 3 | 0.156 s | 0.116 s | 57.08% | 2,642 ms |

Each run processed all 66,000 sent events with zero persistence drops, WebSocket
overflows, sequence gaps, or reconnects. SQLite worker CPU consumed approximately
0.16%-0.34% of one logical core during each nominal measurement minute. The Windows
thread CPU clock advances in approximately 15.6 ms increments, so the exact values are
quantized; their scale is still far below the 25% persistence/delivery investigation
gate. Process CPU and sender latency varied materially across repeats while SQLite CPU
remained small, which provides no evidence that persistence causes the sender backlog.

Source: [three repeated worker profiles](arb022-worker-profile-20260912T095033Z.json).

## Gates for a future change

These are chosen engineering thresholds for deciding whether to prototype a change,
not measured exchange SLAs. Reproduce findings on an otherwise idle host with at least
three 60-second runs, the same lockfiles and fingerprints, and both the representative
110/s case and 10× headroom case. A candidate must preserve decimal strings, protocol
correctness, bounded queues, and all existing tests.

| Proposal | Evidence required before a prototype | Evidence required before adoption |
| --- | --- | --- |
| Faster JSON dependency | JSON consumes ≥15% of non-wait self time in repeat profiles, plus measured decode cost on actual captured frame sizes | ≥20% reduction in process CPU or send→detect p99 at 1,100/s, no >5% representative-rate regression, identical decoded/wire values |
| Tree or alternative sorted structure | Mutation consumes ≥15% of non-wait time, with depth sweeps at 500, 5,000 and 10,000 levels showing repeatable growth under insert/delete churn | ≥20% pipeline benefit at the measured required depth, no >10% RSS increase without justification, exact ordering and Decimal equivalence |
| Threads/processes or event-loop change | Repeatable ≥70% of one core and send→detect p99 >250 ms at the required workload, or sustained queue loss; attribute the limiting CPU/thread first | ≥30% send→detect p99 improvement, zero new losses, bounded handoff queues, shutdown/recovery tests, and documented ordering ownership |
| Persistence/delivery redesign | Repeated drops/overflows or ≥25% of non-wait profile time; separately measure SQLite worker or actual socket-client load | Zero losses at the required rate, ≥20% CPU or latency benefit, no ingestion-blocking handoff |

Current JSON and mutation times are well below their profiling gates. The 1,100/s
sender latency crosses the diagnostic latency threshold, but process CPU is about
27%, not the required saturation evidence. No dependency/architecture implementation
ticket is justified yet. Next evidence should isolate host scheduling, socket buffering,
and SQLite worker CPU, then repeat longer runs before making a causal claim.

The representative workload, stage attribution, separate SQLite worker measurement,
and proposal-specific thresholds complete ARB-022. The 5,000- and 10,000-level depth
sweeps remain a prerequisite only if a future observation crosses the mutation gate and
someone proposes a different book structure. No implementation ticket is justified by
the current evidence.
